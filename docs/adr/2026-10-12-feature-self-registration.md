# Register features from their own files, never a shared list

- **Status:** Accepted
- **Date:** 2026-10-12
- **Card:** REG-01 (infrastructure; amends ADR 0002 and ADR 0007)

## Context

Parallel feature branches kept conflicting because every feature appended to
the same central lists:

- the ACL manifests `build.rs` included (`features/manifest.rs`,
  `organize_manifest.rs`, `recording_manifest.rs`, `manifest_commands.rs`,
  `dev_manifest.rs`) and the `"<name>:default"` grants in
  `capabilities/default.json` (and `capabilities/dev/`);
- `lib.rs`'s `platform_plugins()` / `library_plugins()` and PRV-02's
  `OPEN_WHILE_LOCKED` list in `features/privacy/guard.rs`;
- `features::builders()` / `more_builders()` / `dev_builders()` for the
  bindings;
- `composition.rs`'s `attach_*` calls (and `composition/background.rs`);
- `deino-db`'s `Table` enum, `ALL` and `from_name`;
- `deino-pipeline`'s `registry::stages()`;
- `deino-domain`'s `pub use id::{..}`.

Each list was append-only, so two branches adding a feature touched the same
lines. ADR 0002 rejected `inventory`-style registration because "it hides what
is registered and depends on linker behaviour; the ACL still needs an explicit
list in `build.rs`". This ADR answers both points: the ACL is generated from
the same source the commands come from, and guard tests list what registered.

## Decision

**A feature registers itself from its own files.** The only shared lines left
are module declarations (`pub mod x;` in `features.rs`, `mod x;` in
`composition.rs` and `stages.rs`), kept alphabetical and one per line.

1. **ACL and capabilities: generated by `build.rs` from each feature's
   files.** `build/features.rs` finds every `src/features/<m>.rs` with a
   `src/features/<m>/commands.rs`, reads `pub const NAME` and the
   `collect_commands![..]` list (the last path segment of each entry), and a
   `#![cfg(debug_assertions)]` line for debug-only features. It registers each
   with tauri-build (`InlinedPlugin`, `AllowAllCommands`), copies
   `capabilities/*.json` to `$OUT_DIR/capabilities/` beside a generated
   `features.json` (the `main` window's grant of every feature) and, in debug
   builds, `dev-features.json`, and points `capabilities_path_pattern` there.
   It also writes `$OUT_DIR/feature_acl.rs` for the guard tests. One source of
   truth: the `collect_commands!` that builds the invoke handler and the
   bindings. Hand-written capabilities keep core permissions and the grants of
   windows other than `main` (the meeting prompt, the record panel).
2. **Plugins: a `linkme` distributed slice.** `features/registry.rs` declares
   `PLUGINS: [FeaturePlugin { name, init, specta, access }]`; each feature
   adds itself with `super::registry::register_plugin!(Guarded)` or `(Open)`.
   `lib.rs` registers `registry::plugins()` (sorted by name) behind the
   PRV-02 guard with each plugin's `Access`; `Guarded::new(plugin, access)`
   replaces the name list, and `access(name)` defaults to `Guarded`.
3. **Bindings: the same slice.** `bindings.rs` exports `(name, specta())` of
   every registered plugin.
4. **Composition: attach hooks.** `composition/attach.rs` declares
   `ATTACHMENTS: [Attachment { name, order, phase }]`, where `Phase` carries
   the hook and what it is given: `Local(fn(&Context))` (after the core
   services, before settings are read), `ReadModel(fn(&Context,
   &ActionItemWiring))` (after the LLM gateway and stage services),
   `Background(fn(&Context))` (once the pipeline runs) and
   `Startup(fn(&AppHandle) -> Result)` (end of `setup.rs`). Hooks run by
   `order`, then name, within their phase. Leaf wiring (speakers, vocabulary,
   notepad, sample, player and clips and comments, egress log, fixture
   seeder, stats, briefs, speaker tags, recording, transcript edits, import,
   calendar, integrations, the example) registers with `attach!(name, order,
   phase)`. Shared services that later steps are built from (settings, the
   network, the database, folders and tags, the gateway and search, the stage
   services, notes, the pipeline) stay explicit. `composition.rs` is 227 lines.
5. **Tables: generated from the migrations.** `deino-db/build.rs` replays
   every migration's `CREATE TABLE`, `DROP TABLE` and `ALTER TABLE .. RENAME
   TO` (temporary and virtual tables are skipped; the `_example` migrations
   are read too) and writes one `tables! { .. }` invocation; the macro in
   `table.rs` declares `Table`, `ALL` and a sorted by-name index for
   `from_name` (a binary search, no allocation). The 51 tables that existed
   are a **frozen** list (`build/legacy_tables.rs`) that keeps their order
   (and so `Ord` and `TABLES`) and their docs exactly; a new table is
   appended in migration order and documented by the `--` comment block
   directly above its `CREATE TABLE` (the build fails without one). Variant
   names are the CamelCase of the SQL name, checked to serialize back.
6. **Pipeline stages: a `linkme` slice.** `registry::STAGES` holds
   `fn(&StagePorts) -> Arc<dyn PipelineStage>`; each stage file calls
   `crate::registry::register_stage!(MyStage)`. Order still comes from
   `PipelineStage::order`, and `stages()` sorts by `(order, id)` as before.
7. **IDs: `pub use id::*;`.**

**`linkme` (=0.3.37, MIT OR Apache-2.0).** Chosen over `inventory` because it
needs no life-before-main constructors: each entry is a static in a linker
section (`__DATA,__linkme…` on Mach-O, `linkme_…` with `__start_`/`__stop_`
on ELF, `.linkme_…$` on PE), read as a slice. rustc's `symbols.o` keeps
`#[used]` statics of rlibs, so entries survive linking the app's binary and
test binaries on macOS and Linux alike; the guard tests (and a section-size
check of the built binary) prove it. Its expansion uses `link_section` and an
`unsafe fn` type check, which the workspace's `unsafe_code = "deny"` rejects,
so the three registration macros (`register_plugin!`, `register_stage!`,
`attach!`) and the three slice declarations carry one
`#[allow(unsafe_code, reason = "...")]` each; feature code writes none.

**Guard tests**, rewritten against the new sources:
`bindings::exported_commands_match_the_acl` (the generated ACL allows exactly
what the registered plugins export); `features::acl` (every feature is
granted to `main`, hand-written capabilities grant no debug-only feature,
every ACL feature is registered, the debug-only marker is read);
`features::registry` (unique names, `init()` builds the registered name,
unknown plugins are guarded); `privacy::guard` (the open-while-locked set is
exactly the five PRV-02 plugins); `composition::attach` (unique hook names);
`deino-db` (every schema table is a variant and back, the scanner's rules);
`deino-pipeline` (the stage order). `scripts/check-feature-isolation.sh`
(run by the `deps` gate step) fails when a central file grows a per-feature
list again, and checks `_example` appears in central code only as its `mod`.

## Alternatives

- **Keep the lists, append-only:** conflicts on every parallel batch.
- **`inventory`:** works, but runs constructors before `main` and needs the
  same `unsafe_code` allowance.
- **Build-script discovery for everything** (generate `lib.rs` plugin calls,
  the bindings list and the composition calls from a file scan): no linker
  tricks, but generated Rust for runtime registration is harder to read and
  to navigate than a slice, and composition order would still need a source.
- **Runtime capabilities (`Manager::add_capability`)**: no build-time file,
  but the mock-runtime ACL tests read the generated context, so grants would
  exist twice.
- **`#[path]`-generated module declarations:** would remove the last `mod`
  line, but rust-analyzer and rustfmt handle generated `#[path]` modules
  poorly; one alphabetical line per module rarely conflicts.
- **Alphabetical `Table` order:** simpler than the frozen list, but changes
  `Ord` (so `DbChanged.tables` order) and the bindings; the frozen list keeps
  both identical.

## Consequences

- Adding a feature touches only its own files plus one `mod` line per module
  file (see "How to add a feature" in `docs/changes/REG-01.md`).
- Plugin registration order is now by name instead of hand-grouped. Plugins
  only mount their own commands, events and state, so nothing observes it.
- The capability identifiers for feature grants changed (`features`,
  `dev-features` instead of entries in `main`, `dev-tools`, `dev-example`);
  the resolved ACL per window is the same.
- `Table`'s doc changed its last sentence (no longer "add a variant here"),
  the only change to the generated TypeScript bindings.
- Not covered (follow-ups): `StagePorts`/`StageAdapters` (one field per new
  port), `stages.rs` re-exports, `setup.rs`'s platform steps
  (`attach_detection`, `attach_developer`, `attach_permissions`), the
  frontend registries (they are already per-feature registries) and the
  `deino-core` module list.
